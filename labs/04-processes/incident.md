# Лабораторная 04 — Процессы, сигналы и ресурсы Linux

## Цель

Научиться диагностировать процессы Linux по:

* PID и PPID;
* состоянию процесса;
* потреблению CPU и памяти;
* занятому TCP-порту;
* открытым файлам;
* реакции на сигналы.

Главный принцип лабораторной — не использовать `SIGKILL` как первое решение, а сначала установить причину проблемы.

---

## Использованные инструменты

В работе использовались:

* `ps` — просмотр процессов;
* `pgrep` — поиск процессов;
* `pkill` — отправка сигнала процессам по условию;
* `top` — наблюдение за использованием ресурсов;
* `uptime` — просмотр load average;
* `nproc` — количество доступных логических CPU;
* `ss` — просмотр сетевых сокетов и слушающих портов;
* `lsof` — поиск процессов по открытым файлам и сокетам;
* `/proc/<PID>/status` — детальная информация о состоянии процесса и сигналах.

---

# 1. PID, PPID и дерево процессов

Каждый процесс имеет уникальный идентификатор **PID**.

**PPID** — PID родительского процесса, который создал текущий процесс.

Например:

```text
bash
└── sleep
```

Если `sleep` запущен из текущего Bash, его PPID совпадает с PID этого Bash.

Для просмотра использовалась команда:

```bash
ps -o pid,ppid,user,stat,cmd -p <PID>
```

Также была изучена разница между `jobs` и `ps`.

`jobs` показывает только задачи текущего shell, а `ps` позволяет исследовать процессы операционной системы.

После нового SSH-подключения список `jobs` предыдущего shell уже недоступен.

---

# 2. Состояния процессов

В лабораторной были рассмотрены основные состояния:

* `R` — процесс выполняется или готов получить CPU;
* `S` — процесс находится в прерываемом ожидании события;
* `D` — непрерываемое ожидание ресурса ядра, часто связанное с I/O;
* `T` — процесс остановлен;
* `Z` — zombie: процесс уже завершился, но родитель ещё не забрал его exit status.

Например, процесс:

```bash
sleep 600
```

обычно находится в состоянии `S`, потому что большую часть времени ждёт завершения таймера.

Процесс:

```bash
yes > /dev/null
```

обычно находится в состоянии `R`, потому что постоянно выполняет вычисления.

# 3. CPU и Load Average

Для создания искусственной CPU-нагрузки использовался:

```bash
yes > /dev/null &
```

На VM было доступно:

```text
2 логических CPU
```

Процесс `yes` потреблял приблизительно:

```text
99.9% CPU
```

Это означает, что он практически полностью занимал **один логический CPU**, а не всю вычислительную мощность двухъядерной VM.

## Load average

`load average` и CPU utilization — разные показатели.

Load average учитывает в том числе процессы:

* выполняющиеся или ожидающие CPU (`R`);
* находящиеся в непрерываемом ожидании (`D`).

Поэтому высокий load average не обязательно означает загрузку CPU на 100%.

Например, большое количество процессов в состоянии `D`, ожидающих медленный диск, может создать высокий load даже при относительно свободном CPU.

Значения:

```text
load average: 1.00, 0.76, 0.38
```

показывают среднюю нагрузку примерно за:

* 1 минуту;
* 5 минут;
* 15 минут.

# 4. Сигналы процессов

В лабораторной были рассмотрены основные сигналы:

* `SIGINT (2)` — обычно отправляется foreground-процессу при `Ctrl+C`;
* `SIGTERM (15)` — запрос корректного завершения;
* `SIGKILL (9)` — принудительное завершение ядром;
* `SIGHUP (1)` — исторически сигнал потери управляющего терминала; некоторые приложения используют его для перечитывания конфигурации.

## SIGTERM

Обычное завершение следует начинать с:

```bash
kill -TERM <PID>
```

или:

```bash
kill <PID>
```

По умолчанию `kill` отправляет именно `SIGTERM`.

Процесс может обработать SIGTERM и перед завершением:

* закрыть файлы;
* завершить соединения;
* записать данные;
* удалить временные ресурсы.

## SIGKILL

Если корректное завершение невозможно и причина установлена, можно использовать:

```bash
kill -KILL <PID>
```

или:

```bash
kill -9 <PID>
```

`SIGKILL` нельзя перехватить, проигнорировать или обработать.

Поэтому использование `kill -9` как первой команды является плохой диагностической практикой.

# 5. Инцидент №1 — высокая CPU-нагрузка

## Симптом

На VM вырос load average.

Поиск процессов, отсортированных по CPU, показал:

```text
PID 8917
STAT R
CPU 99.9%
CMD yes
```

## Гипотеза

Процесс `yes` создаёт постоянную CPU-нагрузку.

## Проверка

Было установлено:

* процесс находится в состоянии `R`;
* использует около 100% одного CPU;
* его PPID соответствует текущему Bash.

Попытка:

```bash
kill -TERM 8917
```

не завершила процесс.

При этом exit code команды `kill` был:

```text
0
```

Это означает только то, что сигнал успешно отправлен, а не то, что процесс обязательно завершился.

Проверка:

```bash
grep -E '^(Name|State|SigPnd|SigBlk|SigIgn|SigCgt):' /proc/8917/status
```

показала, что `SIGTERM` находится среди игнорируемых сигналов.

## Исправление

После подтверждения причины процесс был завершён через `SIGKILL`.

## Проверка восстановления

После завершения было проверено:

* PID отсутствует в `ps`;
* процесс больше не потребляет CPU;
* load average начинает постепенно снижаться.

## Вывод

Высокий `%CPU` конкретного процесса ещё не означает, что вся машина использует 100% CPU.

Перед принудительным завершением нужно установить происхождение процесса и проверить его реакцию на обычный сигнал завершения.

# 6. Инцидент №2 — порт занят

Для тестового HTTP-сервера использовался:

```bash
python3 -m http.server 18081
```

## Симптом

Новый экземпляр сервера не мог занять порт.

Для проверки использовался:

```bash
ss -tulpn | grep ':18081'
```

Было обнаружено:

```text
0.0.0.0:18081
python3
PID 8919
```

## Проверка владельца

Команда:

```bash
ps -o pid,ppid,cmd -p 8919
```

показала:

```text
PID 8919
PPID 7969
python3 -m http.server 18081
```

Таким образом было доказано, что порт принадлежит именно лабораторному HTTP-серверу.

## Попытка корректного завершения

Был отправлен:

```bash
kill -TERM 8919
```

Однако:

* процесс остался в `ps`;
* порт продолжал находиться в `LISTEN`.

Проверка `/proc/8919/status` показала, что SIGTERM игнорируется процессом.

## Исправление

После определения владельца ресурса и причины неработающего SIGTERM процесс был завершён принудительно.

## Проверка восстановления

После исправления отдельно проверялись:

```bash
ps -p 8919
```

и:

```bash
ss -ltnp | grep ':18081'
```

Важно проверять не только исчезновение процесса, но и освобождение самого ресурса.

# 7. Поиск процесса по открытому файлу и порту

HTTP-сервер был также найден через `lsof`.

По порту:

```bash
lsof -nP -iTCP:18080 -sTCP:LISTEN
```

По PID и открытому лог-файлу:

```bash
lsof -p <PID>
```

В выводе было видно, что:

* файловый дескриптор `1` — stdout;
* файловый дескриптор `2` — stderr;

оба были перенаправлены в один лог-файл.

Один процесс можно искать несколькими способами:

```text
PID           → ps
имя/команда   → pgrep
TCP-порт      → ss / lsof
открытый файл → lsof
```

# 8. Инцидент №3 — процесс игнорирует SIGTERM

Был создан лабораторный процесс:

```bash
bash -c 'trap "" TERM; while true; do sleep 1; done'
```

Конструкция:

```bash
trap "" TERM
```

настраивает shell на игнорирование SIGTERM.

## Диагностика

Через `pgrep` был найден процесс:

```text
PID 8920
bash -c trap "" TERM; while true; do sleep 1; done
```

Проверка:

```bash
grep -E '^(Name|SigIgn):' /proc/8920/status
```

показала:

```text
SigIgn: 0000000000004004
```

То есть SIGTERM действительно находился среди игнорируемых сигналов.

## Исправление

Только после подтверждения причины был применён:

```bash
kill -9 8920
```

## Проверка

После завершения:

```bash
ps -p 8920
```

не возвращал строку процесса.

# 9. `pgrep`, `pkill` и `kill`

`pgrep` используется для поиска процессов:

```bash
pgrep -af '<шаблон>'
```

`pkill` отправляет сигнал всем процессам, соответствующим условию.

Поэтому безопасный порядок:

```text
pgrep
↓
проверка найденных процессов
↓
pkill
```

Если PID уже известен, предпочтительнее явно обращаться к конкретному процессу:

```bash
kill -TERM <PID>
```

чем использовать слишком широкий шаблон `pkill -f`.

# Итоговые выводы

В ходе лабораторной были закреплены следующие принципы:

1. PID идентифицирует процесс, PPID — его родителя.
2. `jobs` относится к текущему shell, а `ps` используется для исследования процессов ОС.
3. Состояния `R`, `S` и `D` имеют разный смысл и помогают при диагностике нагрузки.
4. Load average нельзя считать процентом использования CPU.
5. 100% CPU одного однопоточного процесса обычно означает загрузку одного логического CPU.
6. Перед завершением процесса нужно установить его назначение и происхождение.
7. `Address already in use` говорит о конфликте ресурса, но ещё не определяет виновный процесс.
8. После завершения процесса нужно отдельно проверить освобождение ресурса.
9. Exit code `0` у `kill` подтверждает отправку сигнала, но не завершение процесса.
10. `SIGTERM` используется для нормального завершения.
11. `SIGKILL` применяется как эскалация после диагностики, а не как универсальный первый шаг.
12. Один процесс можно находить по PID, имени, открытому порту и открытому файлу.

## Алгоритм диагностики

Основной алгоритм, использованный в лабораторной:

```text
Симптом
↓
Определение области отказа
↓
Сбор минимальных фактов
↓
Гипотеза
↓
Безопасная проверка
↓
Исправление первопричины
↓
Проверка восстановления
↓
Вывод и prevention
```

Главный результат лабораторной: процесс не завершается или потребляет ресурс — это ещё не повод сразу применять `kill -9`. Сначала необходимо понять, **что это за процесс, почему возникла проблема и какие последствия будут у вмешательства**.
