# Тема 03 — Пользователи, группы, права и sudo

## Цель

Настроить модель доступа для будущего сервиса WatchOps по принципу least privilege:

- сервис WatchOps может читать свою конфигурацию;
- сервис может записывать журналы;
- отдельный пользователь-наблюдатель может читать только разрешённые данные;
- посторонние пользователи не получают доступ к критичным файлам;
- для исправления прав не используется `chmod 777`.

## Пользователи и группы

Создан системный пользователь:

- `watchops` — пользователь будущего сервиса;
- shell: `/usr/sbin/nologin`;
- отдельная группа `watchops`.

Создан лабораторный пользователь:

- `observer` — имитация пользователя с ограниченным доступом.

Также создана общая группа:

- `watchops-readers`

В неё входят:

- `watchops`;
- `observer`.

## Модель доступа WatchOps

### Основная конфигурация

Файл:

`/etc/watchops/watchops.env`

Модель:

- owner: `root`;
- group: `watchops`;
- permissions: `640` (`rw-r-----`).

Результат:

- `root` может читать и изменять;
- `watchops` может только читать;
- остальные пользователи доступа не имеют.

Сервис не является владельцем конфигурации, поэтому при компрометации процесса он не может самостоятельно изменить критичные настройки.

### Список целей

Файл:

`/etc/watchops/targets.conf`

Модель:

- owner: `root`;
- group: `watchops-readers`;
- permissions: `640`.

Каталог `/etc/watchops` использует группу `watchops-readers` и права `750`.

Результат:

- `watchops` может читать список целей;
- `observer` может читать список целей;
- `observer` не может его изменять;
- остальные пользователи не могут пройти в каталог.

### Логи

Каталог:

`/var/log/watchops`

предназначен для данных, изменяемых сервисом.

Сервису предоставлены права на запись журналов без необходимости запускать его от `root`.

## Права файлов и каталогов

Для файла:

- `r` — чтение содержимого;
- `w` — изменение содержимого;
- `x` — выполнение.

Для каталога:

- `r` — просмотр списка имён;
- `w` — создание, удаление и переименование элементов;
- `x` — проход через каталог и обращение к объектам внутри.

Для доступа к файлу недостаточно проверить только его permissions.

Пользователь должен иметь право `x` на всех родительских каталогах пути.

Для диагностики использовалась команда:

`namei -l <path>`

Она позволяет увидеть права, владельца и группу каждого компонента пути.

## chmod, chown и chgrp

- `chmod` — изменяет permissions;
- `chown` — изменяет владельца и при необходимости группу;
- `chgrp` — изменяет только группу.

Использовались как числовая, так и символьная записи прав.

Примеры:

- `640` = `rw-r-----`;
- `750` = `rwxr-x---`;
- `g+w` — добавить группе право записи;
- `o-r` — убрать у остальных право чтения.

## umask

Исходная `umask` пользователя:

`0002`

Был проведён эксперимент с:

`0027`

Результат:

- новый файл получил `640`;
- новый каталог получил `750`.

`umask` применяется при создании нового объекта и не изменяет permissions уже существующих файлов.

## sudo

Членство пользователя в группе `sudo` не означает постоянную работу с правами root.

Обычная команда продолжает выполняться с правами текущего пользователя.

Повышенные привилегии получает только конкретная команда, явно запущенная через `sudo`.

## Диагностика Permission denied

Использовался следующий порядок:

1. Определить пользователя, выполняющего операцию.
2. Проверить путь к объекту.
3. Проверить `x` на родительских каталогах.
4. Определить применяемый класс прав: owner, group или others.
5. Проверить permissions самого файла.
6. Исправить минимально необходимое право, ownership или group.
7. Повторить исходную операцию.

Во время лаборатории была обнаружена ситуация, когда сам файл имел правильную группу и permissions, но пользователь всё равно получал `Permission denied`, потому что не имел права прохода через родительский каталог.

## Итог

Настроена модель доступа WatchOps по принципу least privilege.

Я умею:

- читать числовые и символьные permissions;
- различать права файла и каталога;
- определять owner/group/others;
- использовать группы для совместного доступа;
- работать с `chmod`, `chown` и `chgrp`;
- объяснять работу `umask`;
- безопасно использовать `sudo`;
- диагностировать `Permission denied` по всему пути до объекта.
