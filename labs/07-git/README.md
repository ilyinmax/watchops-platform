# Тема 07 — Git: рабочая директория, индекс и коммиты

## Цель

Разобраться в базовой модели Git и научиться осмысленно подготавливать изменения к коммиту, сравнивать состояния файлов, восстанавливать случайные изменения и создавать логические атомарные коммиты.

## Основная модель Git

В работе с Git используются три основных состояния:

```text
Working tree -> Index -> Commit
                git add   git commit
```

### Working tree

Working tree — текущие файлы проекта на файловой системе.

Изменения здесь ещё не обязательно войдут в следующий commit.

### Index / staging area

Index содержит снимок файлов, подготовленный для следующего commit.

Команда:

```bash
git add <file>
```

копирует текущее состояние файла из working tree в index.

Если после `git add` снова изменить этот же файл, Git будет иметь одновременно staged-версию в index и более новую unstaged-версию в working tree.

### HEAD

HEAD указывает на текущее положение в истории Git. Обычно HEAD указывает на текущую ветку, а ветка — на последний commit.

`git commit` создаёт новый commit из содержимого index и передвигает текущую ветку на него.

`git push` не создаёт commit, а отправляет уже существующие локальные commits в удалённый репозиторий.

## Просмотр изменений

### Working tree относительно index

```bash
git diff
```

Показывает изменения, которые ещё не добавлены в staging area.

### Index относительно HEAD

```bash
git diff --staged
```

Показывает то, что войдёт в следующий commit.

Перед commit полезно проверять одновременно:

```bash
git status
git diff --staged
```

## Восстановление файлов

### Отмена unstaged-изменений

```bash
git restore <file>
```

Восстанавливает working tree из index.

Незастейдженные изменения файла при этом теряются.

### Удаление изменения из staging area

```bash
git restore --staged <file>
```

Восстанавливает index относительно HEAD, но оставляет текущий файл в working tree.

Таким образом изменение перестаёт входить в следующий commit, но не удаляется из файла.

## .gitignore

В лаборатории использовались правила:

```gitignore
*.tmp
*.log
.env
```

Они исключают временные файлы, журналы и `.env` из списка untracked-файлов.

Проверить, какое правило игнорирует конкретный файл:

```bash
git check-ignore -v <file>
```

`.gitignore` не перестаёт автоматически отслеживать файл, который уже был добавлен в Git.

## Атомарные commits

Один commit должен представлять одно логическое изменение.

Вместо одного большого commit со смешанными изменениями были созданы отдельные commits для:

* демонстрационного файла Git;
* `.gitignore`;
* документации;
* исправления ошибочного имени файла.

Такую историю проще читать, проверять, диагностировать и при необходимости отменять частями.

## Самостоятельный босс

В ходе лаборатории были одновременно подготовлены несколько изменений.

Требовалось:

* разделить их на логические commits;
* не добавить временные файлы;
* восстановить случайно изменённый tracked-файл;
* исправить ошибочное имя файла отдельным commit.

Дополнительно была разобрана ситуация, когда один файл одновременно имеет staged и unstaged изменения.

## Диагностическая поломка

Файл `notes.md` сначала был изменён и добавлен в index, после чего в working tree была добавлена ошибочная строка.

Получилось состояние:

```text
HEAD          — исходный файл
Index         — исходный файл + полезное изменение
Working tree  — полезное изменение + ошибочная строка
```

Использование:

```bash
git restore <file>
```

восстановило working tree из index, поэтому ошибочная unstaged-строка исчезла, а полезное staged-изменение сохранилось.

## Итог

После лаборатории я умею:

* различать working tree, index и HEAD;
* понимать, что именно попадёт в следующий commit;
* использовать `git status`, `git diff` и `git diff --staged`;
* добавлять изменения в staging area;
* безопасно убирать изменения из staging area;
* отменять случайные unstaged-изменения;
* использовать `.gitignore`;
* диагностировать правила через `git check-ignore`;
* создавать логические атомарные commits;
* исправлять ошибочные изменения отдельным commit.
